# Assumptions

Per spec §3 / §122: where the source (PPT) or master spec leaves a detail open, the engineering choice is
recorded here. `[PPT]` = fixed by the source; everything below is an engineering assumption.

## Simulation engine
- **A1. Built-in microsimulation is the default engine.** SUMO + `libsumo` are not available in the
  target environment. All logic sits behind `SimulationAdapter`; a `SumoAdapter` can replace the default
  with no change to agents / coordination / safety / metrics / UI. `NEXUS_SIM_ADAPTER=sumo` is stubbed
  with an install guide.
- **A2. Physics tick = 0.5 s; decision interval = 6 s** (inside the PPT's stated 5–10 s window).
- **A3. Episode = 3600 s simulated** `[PPT: "each episode equals one hour of simulated traffic"]`.
- **A4. Car-following is a simplified IDM** (desired speed, safe gap, comfortable accel/brake). Not
  calibrated to a real corridor — sufficient for relative AI-vs-baseline comparison, not absolute claims.
- **A5. One isolated intersection, 3 lanes/approach** (left / through / through+right). Network scale is
  deliberately small (spec §97, §99).

## Scenarios (R9 §8A / §8B)
- **A23. The eight §8A presets and their metadata.** `objective`, `ai_focus` and
  `difficulty` (`easy`/`moderate`/`hard`/`extreme`) are written per preset in
  `app/scenarios/presets.py`; they are presentation copy, read by the UI only, never by
  the simulation. Difficulty ratings are an editorial judgement. `surge_midway` is kept
  as a ninth, non-required preset (it is the one that exercises `scheduled_changes`).
- **A24. Custom-scenario bounds are engineering caps, not source values.**
  `arrivals_vph ≤ 12000`, `duration_s ∈ [60, 14400]`, emergency / accident rate `≤ 60`/min,
  `violation_probability_scale ≤ 20`, and a lane closure may never seal every lane of an
  approach. They exist to keep the microsim inside a regime where it is meaningful; a
  value outside them is rejected (`422`), never clamped. `ScenarioConfig` also forbids
  unknown fields so no request can introduce a knob — in particular there is no
  scenario-level control over the authoritative safety layer.
- **A25. New demand profiles `safety_stress` and `mixed_crisis`** in
  `config.yaml → demand.profiles` back the `safety_violation` and `mixed_crisis` presets
  (balanced-heavy and asymmetric-very-heavy respectively). Weights and arrival rates are
  engineering choices, consistent with the existing profiles.

## Signal timing
- **A6.** `min_green = 8 s`, `max_green = 60 s`, `yellow = 3 s`, `all_red = 2 s`,
  `emergency_max_priority = 45 s`. Typical urban values; all in `config.yaml`, all enforced by the safety
  layer, none derived from the source.

## RL
- **A7. Custom PyTorch implementations** rather than Stable-Baselines3, so the inspectors can show
  per-step actor probabilities / Q-values / critic values / advantages / reward components (spec §13–18,
  §41–43, §85). SB3 is listed by the spec only "where practical".
- **A8. Discrete action spaces** exactly as the PPT lists (A2C 5, DQN 5, PPO 4).
- **A9. Documented shaping penalties** — a small `switch_penalty` in each reward to discourage signal
  flapping. The spec explicitly permits "engineering-level penalties necessary for safe operation … and
  document them" (§13). Weights in `config.yaml → reward.*.switch_penalty`.
- **A10. Reward normalisation constants** (`/120 s` for waiting, lane capacity for queue, etc.) are
  scaling choices for stable learning, listed in each agent's state-builder.
- **A11. Shipped checkpoints are lightly trained** (hundreds of episodes, CPU). They demonstrate real,
  improving behaviour; they are not claimed to be optimal. Training curves shown are the actual run logs.

## Fuel model (spec §25 — **ESTIMATED, not measured**)
- **A12.** `fuel_l = idle_l_per_s·t_idle + per_stop_l·n_stops + cruise_l_per_m·distance +
  accel_l_per_ms2_s·∫|a⁺|dt`, times a per-vehicle-type multiplier. Coefficients in `config.yaml → fuel`,
  order-of-magnitude values for a light passenger vehicle. Purpose: consistent *relative* comparison
  between controllers, not regulatory accuracy.

## Emission model (spec §26 — **ESTIMATED**)
- **A13.** `co2_kg = fuel_l · 2.31` (kg CO₂ per litre gasoline) `+ cold_start_penalty` per trip. Only CO₂
  is modelled. No NOx / PM. Labelled "ESTIMATED" everywhere it appears.

## Violations (spec §24, PPT slide 12)
- **A14.** No computer-vision detector (the source explicitly does not specify one). Violations are
  generated by the simulation as low-probability events (`config.yaml → violations`) and consumed as an
  indicator by DQN state + reward + safety metrics + timeline.

## Coordination
- **A15.** Priority-ladder weights and `emergency_override_threshold = 0.55`, `consensus_bonus = 0.1` are
  engineering choices in `config.yaml → coordination`. The *structure* (safety → emergency → valid phase →
  congestion → efficiency → throughput → stability) follows spec §21 verbatim.

## Coordination / safety implementation deviations
- **A17. `SafetyValidator.validate()` takes a `PhaseCommand`, not a bare candidate phase.**
  docs/safety.md originally sketched `validate(candidate, state)`. The coordinator produces
  extend/reduce/force intent alongside the target phase, and that intent must survive the
  coordinator → safety hop for the signal controller to act on it, so the validator receives
  the whole command. Behaviour is unchanged; the signature is wider.
- **A18. Rewards for decision N are realised at decision N+1.** The reward needs the state
  that resulted from applying decision N, which only exists one interval later. The A2C/PPO
  rollout buffers set the reward on their last stored step, so this is the correct on-policy
  ordering, not a lag bug.

## Metrics implementation deviations
- **A19. `idle_time_s` is the per-vehicle low-speed `wait` accumulator**, i.e. time below
  `_STOP_SPEED_MPS` (0.3 m/s), not a separately integrated "engine idling" clock. For this
  microsimulation the two are the same quantity; the metric name is kept for continuity with
  docs/metrics.md.

## Frontend
- **A16.** Vehicle positions are streamed at 20 Hz and interpolated client-side to hit the 60 FPS render
  target (spec §72, §115). The authoritative state is always server-side.
- **A20. Per-approach signal aspect (`approach_colors`) is computed server-side** by the
  `SignalController` and sent on the wire, rather than re-derived in the browser from the
  phase. The renderer must show exactly what the controller believes it is showing (spec §114).
- **A21. Agent inspector payloads are polled over REST (2 s), not streamed.** A full inspector
  payload costs one forward pass per agent; at the 20 Hz stream rate that is three extra
  forward passes per frame for data that only changes once per decision interval.
- **A22. Rendered FPS shown on the stage is measured in the browser** via `requestAnimationFrame`
  and is a client display-health number, not a backend metric. Backend loop timings
  (`ai_latency_ms`, `sim_step_ms`, `frame_time_ms`) are separate and come from `dev` metrics.
